核对日期：2026-10-21。此记录仅分析已有代码、静态表及历史抓包，未修改功能，未向游戏发送请求。

## 结论

现有资料足以开始开发当前活动的自动推图。本轮抓包覆盖 `BH610` 首次进入活动、普通关卡 1～11、困难关卡 12，以及精英关卡 13 的完整成功流程。当前活动的主要协议和静态数据齐全，暂不需要再补一轮成功抓包。

这项功能需要增加关卡目录、首次通关处理和活动服务器战斗适配；现有活动扫荡不能直接改成循环递增关卡编号。

## 两类战斗路径

### 普通和困难：HTTP 结算

1～12 关都使用 `SceneHandler.FinishScene`，没有观察到独立的 HTTP 开战或解锁请求。首次通关请求的主要字段为：

```text
SceneData = {StaticID: 当前关卡, Stars: [0,0,0], PassCount: 0}
IsRestart = 0
IsRepeatAuto = 0
IsQuickBattle = 0
FinishWave = 2
Camp2DeadList = 最后一波敌人的临时 UUID 列表
```

本轮每关三波，`FinishWave=2` 为最后一波下标。`Camp2DeadList` 数量与对应静态表第三波敌人数吻合，范围为 3～5。临时 UUID 应按当前请求构造，不能复用抓包中的实例值。

现有 `backend/tasks.py` 的 `_ACTIVITY_META` 用于活动重复扫荡：`IsRestart=1`、`FinishWave=0`、不带 `Camp2DeadList`。首次推图需要独立参数。已有的 `_finish_scene` 提供 `scene_data` 和 `dead_count` 入参，角色装备与助战组装也可复用。

第 2 关的 `MyCampTeam` 指定剧情角色，静态表与抓包一致。当前个人队伍组装器只从账号仓库找角色，需要补充剧情角色的构造逻辑。本期两名角色的定义、技能及示例请求均已具备。

### 精英：WebSocket 战斗

第 13 关静态配置 `ServerBattle=TRUE`。开战、心跳、行动消息、结束回执和奖励帧与已有深渊战斗具有共同结构，可复用通信、行动选择及奖励合并能力。

当前深渊执行器仍有专用假设，需要适配：

- 深渊是上下两队，活动是一支队伍连续打三波。
- 活动使用普通场景的三份 `WaveInfo*JsonString`，不读取深渊 `Fantasy` 波次配置。
- 活动开战支持助战；角色状态初始化需要处理 `RoleStatusInfo1/2` 等活动配置。
- 抓包的 `NowWaveIndex` 包含 0、1、2；现有执行器的进度处理仅接受 0、1。

能复用通信协议，不代表当前深渊执行器已经能直接运行活动精英关。

## 关卡数据与进度

原始 `assets_full/文本/数据表/sd_Scene.txt` 包含关卡编号、`PreScene`、体力、三波敌人、剧情队伍、服务器战斗标记、难度开放活动及星级条件。`BH610` 定义从 1844 行开始，共 14 关。

应从静态表构建活动目录，再用登录快照和结算响应判断通关、开放及可进入状态：

- 登录记录缺少某关，不表示该关不存在或不可进入。首次请求可使用抓包证实的初始记录。
- 通关判断使用 `Stars[0]`。样本通关后 `PassCount` 仍为 0，不能用它判断是否完成。
- 一星通关也应继续前进。第 2、4、6、8、10、12、13 关成功返回 `[1,0,0]`。
- 前置条件应读取 `PreScene`；例如第 12 关要求第 6 关通关，并非第 11 关。
- 第 13 关还要求 `Version_Elite`；第 14 关要求 `Version_Hell`。抓包中精英已开放、地狱没有开放排期，故本轮最后可进入的关卡是第 13 关。
- 活动本身也必须按 `BranchH610` 等族排期过滤，避免推已经结束的活动。

现有活动选项仅遍历登录记录，无法列出全新活动。HTTP 的 `_finish_scene` 目前也没有把返回的 `SceneData` 写回进度，且只按掉落判断成功。自动推图应核对结算关卡及 `Stars[0]`，合并返回的关卡、账号、角色、任务和余额后，再计算下一关；可复用已有 `GameClient.apply_scene_reward` 的字段合并能力。

当前资源生成器只把 `MysteriousRealm_*` 场景打包进 `assets/abyss_battle_static.json`，没有活动场景目录。开发时需从现有原始表生成活动所需的小型资源，并接入正常资源更新流程。

## 资料覆盖边界

本期 `BH610` 所需敌人和剧情角色定义齐全。额外检查了全部 966 条、69 个活动族的场景定义，三波、剧情队伍及角色状态字段均可用现有 DSL 解析器解析。

全历史目录有少量角色引用未在当前角色表中找到：`BranchH107/H108/H110/H111/H169/H205`。这些不属于本次抓包开放的活动；跨活动支持应校验引用完整性，不能承诺全部历史族都能直接运行。

本轮没有活动失败、体力不足、满背包、战斗中断线或地狱首次通关样本。它们不阻止开始实现当前活动的成功链路，但异常时应停止并保留待确认状态，避免从旧进度重复花费。补充这些样本有助于细化错误提示和恢复策略。

## 页面及执行建议

在现有“活动关卡”选项内增加“扫荡 / 自动推图”两页，沿用现有通用样式。“自动推图”选择活动、队伍和助战，按关卡前置及开放条件，从首个未通关关卡继续推进，展示当前关卡与完成进度，支持手动停止。

本期完整目标应包含普通、困难与已开放的精英关。根据 `ServerBattle` 选择 HTTP 或 WebSocket 路径，逐关确认后继续；已通关关卡直接跳过，未开放难度不纳入本轮目标。

## 实现记录（2026-10-21）

已实现“主动任务 → 活动关卡 → 自动推图”。普通和困难关使用独立的首通结算参数；精英关复用 WebSocket 通信与 AI，支持单队连续三波、助战和结束奖励合并。每关读取 `MyCampTeam`，剧情队伍可以出现在任意位置，不固定为第二关。队伍和助战选择沿用活动扫荡控件，模式与选择按账号保存。

运行资源继续使用已有的 `assets/abyss_battle_static.json`，生成器扩展其 Scene 表为 10 个深渊场景和 966 个活动场景，保留前置、开放条件、体力、波次和剧情队伍等字段；正常资源同步自动包含这项产物。启动时校验所选活动的角色引用；历史缺失引用不会阻止其它活动的资源构建。

新增 `/api/activity/progress/run` 和 `/api/activity/progress/cancel`，进度随已有日志轮询返回。每次结算必须收到当前关卡的通关星级才继续，一星有效。失败、体力不足和手动停止终止当前序列；请求发出后若断线或没有确认结算，保留“等待登录同步刷新”标记，禁止从旧快照再次推图。完整登录替换快照后解除该标记。发起请求前取消不会留下待确认标记。

额外核对客户端 `SceneRoleStatusInfo.InitBattleRoleData`（`0x22183cc`）及闭包：队伍中的活动角色潜能决定队伍加成；`Activity_Main` 只作用于对应角色，并临时提升战斗副本的等级、星级、觉醒和技能。助战中的活动角色独立获得此状态，不回写仓库。支持服务器 `NewSupportRole` 替换身份，后续行动使用服务器身份及当前敌方波次。

验收包括 `tools/test_activity_progress.py`、`tools/test_activity_progress_ui.py`、资源生成测试及原有深渊/活动刷新回归。BH610 精英历史抓包离线回放覆盖三波、37 次客户端行动、终局回执和奖励合并；UI 在 360 / 390 / 1280 宽度、深浅主题下验证模式切换、账号隔离、停止和加载失败重试。离线固定响应不会按新行动重算战果，仍需实号验证；本轮没有向游戏发请求。
